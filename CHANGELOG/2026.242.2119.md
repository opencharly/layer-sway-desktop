# 2026.242.2119 — chore(sway-desktop): advance the xfce4-terminal pin to v2026.242.1906

## Summary

`layer-xfce4-terminal` fixed two stale pins that declared dependencies as **bare names**
instead of full `@github` refs (opencharly/layer-xfce4-terminal#3), taking its own
`charly box validate` from exit 1 to exit 0.

This repo still pinned `v2026.237.1057`, which predates that, so it re-introduces the old
edge into any project that composes this candy.

### The diff, in full

Two lines change in `charly.yml`:

```
- '@github.com/opencharly/layer-xfce4-terminal:v2026.237.1057'  ->  v2026.242.1906
  version: 2026.242.1712                                        ->  2026.242.1930
```

The second is this candy's OWN version. Any change to a candy's content needs a new CalVer,
or different content ships under a version already released. `2026.242.1930` is the standard
`YYYY.DDD.HHMM` stamp at the time of the edit (day 242, 19:30), matching the convention used
across the org; it carries no meaning beyond ordering.

### Measured, not assumed

In a downstream project this is one of exactly **two** remaining
`resolved to multiple versions` sources, identified by repinning consumers one at a time and
re-reading the count:

```
ignoring 2026.144.1443 (from github.com/opencharly/layer-xfce4-terminal@v2026.237.1057)
ignoring 2026.187.1200 (from github.com/opencharly/plugin-wl@v2026.240.1326)
```

Worth recording the mechanism, because it is counter-intuitive: that project read **0**
warnings before this line of work, not because its graph was consistent but because it was
uniformly **stale** — every consumer pinned the same old versions. Advancing any node
unmasks conflicts those identical old pins were hiding. Verified in both directions: an
unrelated repin of three selkies pods took the same project from 2 warnings to 7 and was
reverted on that measurement alone, exactly as an earlier `layer-chrome-sway` repin took it
from 3 to 6 and was likewise reverted.
