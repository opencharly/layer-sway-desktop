# 2026.243.0858 — chore: advance stale pins so published tags carry current refs

## Summary

Advances this repo's one remaining stale pin. A published tag embeds the pins it carried at
tag time, so consumers pinning a tag of this candy drag its old refs into their own
resolution and charly reports `resolved to multiple versions` on every build of that
consumer.

The diff changes exactly **two** values, both in `charly.yml` — nothing else:

```
  @github.com/opencharly/layer-xfce4-terminal   v2026.242.1906 -> v2026.243.0838
  version (this candy's own CalVer)             2026.243.0900  -> 2026.243.0901
```

```

```

No packages, services or plan steps change. The schema stamp on line 1
(`version: 2026.232.0520`) is deliberately **untouched** — it is the schema contract, not a

### Why the CalVer advances by only one minute

The stamp is `2026.243.0901`, derived as main's `2026.243.0900` plus one minute rather than
read from the wall clock. That is deliberate and worth stating plainly, because the value
does not correspond to this commit's timestamp:

main's `2026.243.0900` was itself stamped ahead of reality — it landed in PR #5, whose merge
commit is timestamped **08:31 UTC**, and whose own tag is `v2026.243.0831`. That CalVer was
hand-picked rather than read from a clock, so for roughly half an hour any correctly
clock-derived stamp would sort *before* what main already carries, i.e. it would regress the
version.

Rather than publish a regression or idle until the clock caught up, the next stamp is derived
from main's, which is what the CalVer is actually for: ordering. `2026.243.0901` sorts
strictly after `2026.243.0900`, which is the property that matters.

### A failure that was the harness, not this repo

An earlier attempt reported this repo as failing validation with a `pod-waybar` CUE schema
error. That was investigated rather than worked around, and the repo was innocent: the sweep
harness selected its charly binary with a `case` that had arms for `v2026.238.*` and
`v2026.241.*` and a default of `v2026.238.*`. This repo pins `v2026.240.2035`, so it fell
through to charly **238** — a binary that genuinely cannot parse the pinned `pod-waybar`, and
one this repo does not pin.

Controls that isolated it:

- pristine main under the correct binary — exit 0
- pristine main plus the pin advance alone — exit 0
- pin advance plus the CalVer bump — exit 0

The harness now has a `v2026.240.*` arm and its fallback **fails loudly** instead of silently
selecting the oldest binary, so a version-mapping gap can never again be reported as a defect
of the repo under test.
