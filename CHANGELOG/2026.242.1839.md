# 2026.242.1839 — fix(sway-desktop): advance stale pins — green gate, and the last skew source

## Summary

Two things, and the second is why the first could not land alone.

### 1. The xdg-portal pin was stale, and is a version-skew source

`layer-xdg-portal` gained an `arch:` section (opencharly/layer-xdg-portal#2), so it now
installs on Arch/CachyOS instead of only Fedora. This repo still pinned `v2026.237.557`,
which predates that — a sway desktop composed from here on a CachyOS base would get a portal
candy that installs nothing.

It is also the last **transitive** skew source. Any project composing both this candy and a
newer `layer-xdg-portal` resolves the same candy at two versions, on every build:

```
Warning: candy github.com/opencharly/layer-xdg-portal resolved to multiple versions;
using newest 2026.242.1655 (from …@v2026.242.1648), ignoring 2026.144.1443 (from …@v2026.237.557)
```

Measured, not assumed — the same downstream bed, same host image, three runs:

```
2026.242.1607: 0 multi-version warnings   <- before any consumer pinned layer-xdg-portal
2026.242.1652: 3 multi-version warnings   <- after a consumer pinned v2026.242.1648
2026.242.1704: 3 multi-version warnings   <- after repinning every DIRECT consumer
```

The third line is what identifies this repo: repinning all direct consumers left the count
unchanged, so the surviving pin had to be transitive.

### 2. This repo's gate was already red, which blocked that one-line fix

`charly box validate` fails on unmodified `main` with 4 errors, all one class — the pinned
versions predate the move from BARE dependency names to full `@github` refs, so their
declared dependencies resolve to nothing:

```
candy "…/layer-wf-recorder" depends: unknown candy "plugin-record"
candy "…/layer-asciinema"   depends: unknown candy "plugin-record"
candy "…/pod-chrome-cdp"    depends: unknown candy "plugin-cdp"
candy "…/pod-chrome-cdp"    candy:   unknown candy "chrome-devtools-mcp"
```

Bisected by advancing one pin at a time and re-reading the error count: `layer-wf-recorder`
and `layer-asciinema` clear the two `plugin-record` errors. The `pod-chrome-cdp` pair is
transitive through `layer-chrome-sway`, and was fixed at its root in
opencharly/layer-chrome-sway#2 rather than papered over here; this picks up that release as
`v2026.242.1719`.

Four pins move. No packages, services or plan steps change.

Run with charly **`v2026.238.1242`** — the version this repo's `deploy.yml` clones and

## Reconciling the pasted evidence (validator findings)

**`2026.144.1443` is not this candy's version.** It is the INTERNAL candy version of
`layer-xdg-portal` at the old tag, which is what charly names in the warning. Verified by
fetching that tag directly:

```
$ gh api "repos/opencharly/layer-xdg-portal/contents/charly.yml?ref=v2026.237.557" \
    --jq '.content' | base64 -d | grep -m2 'version:'
version: 2026.232.0520          <- schema stamp
        version: 2026.144.1443  <- the candy's own version, the number in the warning
```

The collision is real but coincidental: this candy's own version was ALSO `2026.144.1443`
before this PR bumps it, because both were scaffolded from the same default. Charly's warning
reports candy `version:` fields, while the `@vTAG` refs are git tags — two different numbering
schemes in one message, which is what made this look irreconcilable.

**`2026.242.1607/1652/1704` are not charly versions.** They are bed-run directory names
(`.check/check-punktfunk-fleet/<calver>/`), i.e. timestamps of three runs. The gate binary is
charly `v2026.238.1242` throughout, as stated. Relabelled here because the original
presentation invited exactly this reading.

**On the zero-warning demand.** This PR cannot itself produce a bed run at zero warnings, and
the reason is ordering rather than reluctance. The old pin this removes is consumed
TRANSITIVELY: a project sees it only by resolving `layer-sway-desktop` at a released tag, so
the count can only drop once this merges and tags and a consumer repins to it. Measured
directly, a local shadow does not substitute — charly still collects the remote ref's
manifest for version resolution, so shadowing this candy left the count unchanged.

What IS demonstrated: this repo holds the last remaining old edge among the direct
consumers. Repinning every direct consumer left the count at 3; only the transitive pin here
survives. The consuming project's PR carries the zero-warning run once this is tagged.
